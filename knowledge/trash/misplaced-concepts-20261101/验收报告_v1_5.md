  # 精读驱动的申请书迭代验收（H/M/L issue 分级法）

  ## 林赛的理解

  我经手过太多次"写完即交"的申请书，最后被评审人一个词一个词地拆。这份验收报告体现的做法是我认可的：**申请材料不是靠感觉升级，而是靠逐文件精读登记 issue 来驱动迭代**。v1.4 → v1.5 这一轮，5 份立项/方法学报告（共 270.1 KB）被逐字精读，登记出 12 高 + 23 中 + 29 低 = 64 个 issue，再按"必修/建议修/待补"三档排优先级。这和我们管线里 critic 按维度打分是同一逻辑：先量化缺陷，再谈修改。尤其值得注意的是跨方向一致性检查——T2/T3/T5 三份报告出现同样的附录编号重复，T1/T3/T4 的"4 重优势"实际写成了 5/5/7 重——这类错误靠作者自查几乎必然漏掉，只有独立精读能暴露。我自己的经验是：方向越多（这里 4 个方向并行），这类"局部一致、全局矛盾"的问题越多，精读必须覆盖全部方向而不是抽查。

  ## 核心要点

  - **三级 issue 分级（H/M/L）**：H = 物理逻辑漏洞、数字与正文不符（如节 1.2 "6 类"→"5 类"、"4 重"→"7 重"）；M = 术语不一致、引用缺失、数据点错误；L = 节编号跳跃、跨方向协同标记。
  - **必修 issue 收敛到可执行工作量**：9 个 H 级必修项合计仅 4.5h 工作量，说明精读的价值不在发现"大问题"，而在把大问题压缩成可排的修复清单。
  - **悬而未决决策单独建账**：4 份报告累计 40 项悬而未决（26 用户决策 + 14 AI 调研待补），与 issue 修复分离管理——修改文字和拍板决策是两类不同性质的工作。
  - **跨方向一致性是重灾区**：附录编号重复、优势数量口径漂移、节 3 与节 4 子问题数矛盾，全部出现在多方向并行写作的场景。
  - **验收即状态快照**：验收报告记录"完成什么、推迟什么、下一步什么"（A 选项 20% 完成度如实标注推迟项），而非只报喜。

  ## 实验/研究关联

  - 对应课题库中 NSFC 申请书的章节评审 + 整体一致性评审环节：本报告中的"必修 issue 修复（4.5h）"等价于管线中 writer 按 critic 反馈修订的闭环。
  - 与本项目 v7.2.19 评分锚定改革同源：数字口径漂移（"4 重"实写 5/7 重）正是 rigor 维度"数值链一致"核查要抓的缺陷类型。
  - H 级 issue 中的"物理逻辑漏洞"与评审团 panel_review 的 researcher/critic/reviewer 三角色独立评审互补——机器精读抓硬伤，人审抓科学判断。
