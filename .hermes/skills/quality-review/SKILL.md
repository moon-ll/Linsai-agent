# 质量评审标准（quality-review）

critic 对抗评审、monitor 独立复评、研究设想评审（idea_review）的评审方法学。

**评审定位（v7.0.2 用户裁决 2026-09-26）**：产出的课题文档是给研究人员的研究手册（见 research-proposal skill 〇节），不是给评审人的申请书——评审的首要问题是"研究人员能否据此直接开工"（可执行性），其次是科学正确性，再次才是语体风格。**具体性不足（操作性五问缺答、参数/序列/时间预算缺失）是比语体瑕疵更重的扣分项**；不得以"范本也就写到这个深度"为由放过操作细节缺失。

写作风格维度扣分依据见 nsfc-writing skill 第十节；量化评分档位见 memory/nsfc-standards.json 的 scoring_rubric（注意：部分档位按申请书范本校准，手册定位下"可行性"维度按可执行性从严掌握）。

## 一、四维锚点评审法（critic）

1. 创新性（innovation）：科学问题是否新颖、方法是否有突破——锚点：与最近邻工作的逐项增量对比
2. 可行性/可执行性（feasibility）：技术路线能否落地、是否有支撑——锚点：研究方案的操作性五问**逐问核查**（见 research-proposal skill），任何一问缺答按 high 以上计；时间预算与机时匹配不答不算通过
3. 严谨性（rigor）：**五项核查清单逐项判定**（v7.2.17 清单化，见 scoring_rubric.rigor._checklist_v7217）——①数值链一致 ②指标定义可操作 ③文献支撑真实 ④逻辑闭环 ⑤模块自洽。**按过项数定档**（全过 0.90+/过四 0.80+/过三 0.70+/过二 0.60+/过一以下），禁止印象式打分；0.70-0.79 档必须指出未过的具体项与位置
4. 表达质量（expression）：连贯叙述、无 AI 味、语体对标范本（范本是语体参考非深度锚）——受程序化天花板约束
每个维度引用 scoring_rubric 对应档位描述作为依据，不得凭感觉打分。锚点对比三步法：引申请书原文一句 → 引范本锚点一句 → 写差距一行。

### 一之二、分数锚点校准纪律（v7.2.17）

实测背景：全部课题长期震荡在 0.70-0.85 平台带、rigor 连续占最弱维度
71%（169/237 轮）——印象式打分让 critic 与 writer 在"术语不一致/口径
模糊"的主观判定里循环，修复无靶点；而评审团亲审修复后的复评直接给
0.89-0.91，说明常规 critic 评分存在系统性压分锚偏。校准纪律：

1. **先数档再打分**：rigor 先按五项清单数过项数定档位区间，再在区间内微调；其余维度先对照档位描述定区间。禁止跳过定档直接给分
2. **0.90+ 锚 = 亲审通过质量**：五项全过即给 0.90+，不得因"再看看总有毛病"压档——亲审实证（v7.2.13 十课题）表明清单全过的文本复评为 0.89-0.91
3. **禁止折中摇摆**：0.70-0.85 平台带连续多轮无档位变化的评分视为未完成锚点义务——要么给出未过清单项的具体位置（降档有据），要么承认过项数上调（升档有据）
4. **writer 修复闭环**：critic 意见必须映射到五项清单的编号（如"②指标定义：X 判据无计算式"），writer 修复后下一轮 critic 对同项先核对再计分，已修复项不得重复扣分

## 二、串通与通胀检测（monitor 独立复评）

monitor 不复述 critic 结论，独立评估并检测 writer-critic 串通迹象：
1. 连续多轮 critic 高分 + writer 微调（评分通胀但质量无实质推进）
2. critic 指出的问题被 writer "表面修复"（改了措辞未改实质，如换词降级而非补数据）
3. 分数与锚点结论背离（评分 0.9 但锚点对比"差距明显"）
4. critic 过严（连续多轮同类问题重复扣分且已修复）

## 三、研究设想评审（idea_review 四维）

新设想进入优化前的前置门槛，各 0-1 分，总分 ≥0.70 通过：
1. **清晰度**：核心科学问题一句话可判定，不是方向名词的堆砌
2. **可检验性**：validation 模块给出判据、对照与独立交叉验证路径
3. **切分合理性**：六模块齐备且 route 能落到方案六要素（见 research-proposal skill）
4. **一致性**：与现有课题边界清晰（comparison 说得出增量），无换皮

## 四、评审纪律

1. 评分上限锚定：自评分与锚点结论不一致时，以锚点结论对应档位上限为准，先自行修正再提交
2. 问题必须具体到位置与原文摘录，附可执行修改建议；禁止"建议进一步加强"式空话
3. 历史问题逐条核对当前文本实际状态，严禁因曾出现就重复机械扣分，也严禁未核实就标"已解决"
4. 解析失败（输出过短/格式崩坏）时分数无效，不进入奖惩，不误扣

## 五、评审团 = 执行者无关的流程契约（v7.2.81 用户裁决，修正 v7.2.77）

评审团的本质是**流程契约**（本节五步流程 + 六节角色/findings 契约 +
七节修改/复核纪律 + 评审标准一/一之二/四节），**不绑定任何模型**。
评审员 = 发起评审团的 agent 本身——由该 agent 亲自读文、定点核查、
直接修改、复核判定。这正是"多入口评审团"的意义：任何 agent 入口
（ZCode/CoPilot 会话、其它 CLI agent、人工评审会话）都按同一契约
开展评审团，产出同构、可比、可审计（`06_panel/` + 下游状态机共用）。

- **引擎亲审（正轨，v7.2.81 用户裁决）**：协作引擎在会话内亲自执行
  五步流程，不调用其它 LLM、不外包给固定内置模型。用户明示"过一遍
  评审团"、验收前把关、硬骨头课题均走此通道。
- **任务包交接（v7.2.97，engine 执行器默认）**：panel_review.py 默认
  为**任务包发射器**——不调 LLM、不改文件，产出
  `06_panel/panel-task-package.md` 自包含任务书（核查靶子 + 本契约指引
  + 标准收尾命令 `--adopt-engine`）；任何 agent 入口按包执行，cron
  `lc-panel-review` 因此幂等零撞车。
- **脚本 hermes 编排（无人值守托底执行器，显式 opt-in，非"评审团"本体）**：
  memory/config/panel-executor.json 置 `"executor": "hermes"` 时——
  panel_review.py 经 hermes 三角色执行同一契约。其产出属**自动化预审**
  性质：重要课题定谳仍须引擎亲审复核（预审 findings/verify 报告是亲审
  的输入之一，不是结论）。

**触发**：pending_review 验收前，或 optimizing 平台期（连续 4 轮
|Δ|<2%）/ 完成 r3，或用户明示"过一遍评审团"。

**五步流程**（执行者按此执行）：

1. **定点核查**：对历史遗留问题清单逐条核对当前文本（引用行定位），
   发现同类新问题一并记录（≤5 条防膨胀）。核查维度按本 skill 一~三节
   标准：科学正确性（引用真实性/口径一致）、可执行性（操作性五问）、
   表达红线（AI 模式/超长句/自引用）。
2. **深度修改**：逐条处置核查发现——critical/high 必修；数值/引用类
   修改只采信核实过的来源，禁止凭记忆改写；跨章重复按"单一出处+指针"
   收敛（纪律细目见七节）。
3. **复核**：以修改后的磁盘文本为准，逐条判定已解决/部分/未解决，
   输出 `06_panel/panel-verify-report.md`。
4. **判定**：全部解决或带合理豁免 → 通过，clear_panel_request 恢复
   自动循环；任一 critical/high 未解决 → 需返工并给出收窄清单。
5. **收尾清账**：open_critical_issues 未解决条目标记 resolved_by，
   human_queue 状态刷新。

**纪律**：不因"我是执行者"放松标准——复核必须以修改后的磁盘文本为准
重新核对，不得凭修改时的记忆放行；每轮的返工清单是下一轮的精确靶子。

## 六、评审团角色与findings契约（v7.2.77/97，全执行者通用契约）

panel_review.py 只做流程编排；三角色职责与本节 findings 输出契约
注入各角色 prompt（与常规链路共用真相源，skill 改版即生效）。

**三角色定点核查职责**（互不锚定，各管一段，不越界）：

- **researcher（科学内容审稿人）**：核查科学论证的准确性、文献引用
  真实性（抽查 DOI/arXiv 元数据）、方法与结论的支撑度。不评文风。
- **critic（表达红线审稿人）**：核查超长句、自引用、模板句式、冗余
  修饰等 AI 写作模式与叙事红线。不重复科学性判断。
- **reviewer（评审标准审稿人）**：对照 NSFC 面上项目评审要点（科学
  问题聚焦、指标口径一致、方案-指标闭环、国内现状表述），给出修改
  优先级。

**findings 输出契约**（panel-{role}-findings.md）：

1. 遗留问题核对：逐条给状态（仍存在/已解决）+ 当前文本证据（引用行）
   + 修改建议。
2. 新发现问题 ≤5 条，每条一行表格行：
   `| P<序号> | <critical|high|medium|low> | <章节§位置> | 问题一句话 | 修改建议一句话 |`
3. 问题必须具体到位置与原文摘录，禁止"建议进一步加强"式空话
   （四节纪律同样适用于评审团）。

## 七、评审团修改与复核纪律（v7.2.77/97，全执行者通用契约）

**writer 深度修改纪律**（一次性深度修改 → panel-writer-modification-report.md）：

1. 逐条处置核查发现全部条目：critical/high 必修，medium/low 酌情，
   不适用的在报告标注理由；处置取值：已修 / 部分修改 / 不适用+理由。
2. 数值/口径类修改必须与课题 `04_proposal/params.json` 口径表一致
   （有表时）；口径表之外的数值修改须先核实来源。
3. 引用真实性零容忍红线：文献条目（作者链/标题/期刊/卷期页/DOI/
   arXiv ID）逐字段对照检索池真实记录誊写——池源：`02_literature/
   targeted-research/lit-gap-*.md`、`candidates-*.bib`、
   `02_literature/reading-notes.md`。禁止凭记忆生成或改写任何字段；
   池中无对应记录的条目一律不得写入（宁可少一条，不可编一条）。
   违反按 critical 计（rigor 清单③文献支撑真实——不过）。
4. 修改报告逐条记录：`| # | 问题 | 处置 | 修改位置 | 说明 |`。
5. 评委与 writer 尽量异源：同一模型既当评委又当修改执行者存在自偏好
   风险（评委放过自己的手笔）；降级链（kimi/claude/glm）天然异源于
   主模型，同源不可避免时以结构化契约 + 锚点纪律抑制。

**辩驳-仲裁子流程（v7.3.60 批次 C，对标 MAD 争议点单点仲裁）**：

1. writer 深度修改阶段对**实质不同意**的 finding，不硬修也不裸退回——产出
   `06_panel/panel-rebuttal.md` 结构化反驳行（脚手架 `panel_review.py
   --rebuttal-scaffold PID` 生成，条目号与台账枚举同序）：反驳主张 + 依据
   （口径表/检索池/正文行号，禁止凭记忆）+ 建议处置；**未填行 = 默认接受
   finding**（按原建议修复）。
2. 仲裁 = 对 contested 子集的**单点复核**（不触全轮重评）：逐条裁决
   uphold_finding（维持，writer 必修）/ uphold_rebuttal（反驳成立，finding
   撤销）/ partial（部分成立，按仲裁理由收窄），落
   `06_panel/panel-arbitration.md` 裁决表 `| 条目号 | 裁决 | 理由 |`。
3. 落账：`panel_review.py --arbitrate PID`——uphold_rebuttal 与引擎亲审
   清账同口径（resolved_by=panel-arbitration-<date>）；uphold_finding /
   partial 保持 open 附仲裁注。verify 核销表对仲裁条目按裁决结果判定
   （uphold_rebuttal 视同豁免口径，不阻断晋级）。
4. 效率纪律：仲裁只扫 contested 子集、全程 ≤1 个复核 pass；辩驳率异常高
   （>50% findings 被争议）视为 writer-critic 锚点失配信号，转判据校准
   账本核查，不得以连续辩驳替代修复。

**verify 收尾判定**（panel-verify-report.md，critic 执行）：
1. 对照问题清单 + 修改报告，以修改后的磁盘文本为准逐条核销——核销表
   每条一行：`| <条目号> | <critical|high|medium|low> | 已解决/部分/未解决 | 文本证据 |`
   （条目号：历史问题 `L<序号>`、新发现聚合条目 `C<序号>`，级别沿用
   问题清单/聚合条目表的严重级）；已修复项不得重复计为未解决
   （一之二·4 意见映射纪律同样适用）。
2. 末行总结：`复核结论: 通过`（全部解决或带合理豁免）或
   `复核结论: 需返工`（任一 critical/high 未解决）。

## 八、验收预判（引擎亲审的验收前把关，v7.2.103 沉淀）

pending_review 课题的人工验收会话前，评审员（任何 agent 入口）可执行
**验收预判**：把「从头读申请书」压缩为「对照预判报告逐项过目」。

**触发**：用户指令「验收前判断一轮」；或批量验收前的预检。

**四步流程**：

1. **数据源时序审计**：决策包三档结论由 `monitor_history[-1]` 驱动——
   先取 monitor 末条 `at` 与课题 `updated_at` 对比，**monitor 早于最近
   状态变更即数据陈旧**（决策包 v7.2.103 已自动降级 reject_lean 并标注，
   但预判仍须逐条确认）。账本未清数、口径冲突文件（params-conflicts.json）
   同为输入。
2. **文本级核验**（四节纪律-3 的验收版）：对旧 monitor/账本挂账的每条
   高危问题，落回**当前磁盘文本**逐条核对——引用挂钩 grep + 上下文句读、
   数值口径对照 params.json、结构性公式检查。严禁因「曾出现」就推断
   仍存在，也严禁未核实就标已解决。
3. **联网三源核实**：存疑点用三个独立源交叉（arXiv 摘要页 / arXiv HTML
   正文 / 库内全文缓存或出版社页）；引用类修改只采信核实过的来源；
   摘要级不可判定的明确标「待刊版对照」，不硬改。
4. **分级判定与交付**：逐课题给 approve_lean / attention / 需返工 +
   逐条证据（位置+原文摘录）；交付预判报告（数据源时序表 + 判定表 +
   证据），法定采纳节点仍留人工。

**纪律**：预判是验收的输入不是结论；发现实锤问题可直接修复（走深度
修改纪律七节），修复记录归档 `06_panel/acceptance-fix-record-<date>.md`；
修复后残留扫描（被改关键词全文复扫）为必做收尾。

## 九、方法手册就绪度评审（v7.3.0 第六模块）

方法手册（03_method/method-manual.md）自 v7.3.0 起为生命周期第六评审模块
（method_manual）——课题产出的目的是提供**可以开展**的课题，手册的详细程度
与完整度决定课题能否正式开工。手册就绪度是验收硬门：L≥3 且 2 维分达标才可
approve_lean / 归档。

**评审对象与标准**：八要素清单与 L0-L4 分级的单一真相源在
`method-manual` skill 四节（.hermes/skills/method-manual/SKILL.md），
评审时按该清单**先数档再打分**（本 skill 一之二锚点纪律同样适用：
L4=0.90+ 锚、L3≈0.85、禁折中摇摆、意见映射要素编号①-⑧）。

**口径**：手册走 2 维专用口径 manual_2d——严谨性（rigor：参数溯源/可复算/
口径一致）+ 就绪度（readiness：八要素覆盖与 L 分级）；创新性/可行性/表达
质量 N/A；语体锚点对比不适用（手册是操作文档，非申请书正文）。

**验收预判补充**（八节流程增补第 5 步）：手册未过线（L<3 或有 critical/high
缺口）的课题，即使 monitor/可执行性双门达标，判定也至多 attention——
"手册未达开工就绪"为不可豁免项，须回炉 method_manual 模块升级后再验收。
